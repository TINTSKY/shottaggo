# 标注容量压力测试

- 日期：2026-11-12
- 环境：DeepSeek Harness 0.2.2-rc.1 · Desktop · Edge headless（Chromium）
- 被测产物：`client.js`（166–168 KB，与当前提交一致）
- 脚本：`test/bench/run.cjs`

## 方法

用 `test/harness` 的真实 React 挂载和真实 `client.js`，mock 一个 1485×1284 CSS、1600×1383 栅格的 Browser guest，然后通过 guest 的 `console-message` 协议模拟逐条选择，走完整的“选择 → 评论卡片 → 添加 → 插入”链路：

- 每条标注都有独立评论（约 95 个汉字）。
- 单图场景：N 条标注落在同一张截图上。
- 多图场景：每 5 条标注滚动 300px，生成一张新截图。
- 指标：`PerformanceObserver('longtask')`、`performance.memory`、`createImageBitmap` 读取 PNG 尺寸，插入耗时从点击「插入输入框」到附件进入草稿。
- **注意**：`addAvg ≈ 83ms` 是测试脚本固定等待的 5 个渲染帧（5 × 16.7ms），不是插件的单条处理耗时；插件自身的开销以 long task 和插入耗时为准。

## DSH 的硬限制

来自 `@deepseek-ai/dsh-attachment-local` 的默认值：

- `maxImagesPerMessage = 20`（单条消息图片数）
- `maxImageBytes = 50 MB`（单张）
- `maxMessageImageBytes = 200 MB`（单条消息总量）
- `maxImagePixels = 64,000,000`、`maxImageDimension = 由部署决定`

插件每张截图一个附件，所以**单次插入最多 20 张截图**；超过时宿主会在发送阶段以 `TOO_MANY_IMAGES` 拒绝整条消息。现在插件会在插入前拦截并给可读的错误，不会生成 21 个附件。

## 结论

1. **纯性能不是瓶颈。** 单张图 1000 条标注仍能在 ~135ms 内完成红框绘制 + PNG 编码；JS 堆 <10MB；插入期间最长任务 ~131ms。没有出现卡死、丢标注或内存膨胀。
2. **真正的限制是模型可读性。** 1000 个编号红框挤在一张 1600px 图上，人和模型都无法可靠地把编号与评论对应。实测每条约 95 字的 caption，在 30 条时约 2.8k 字符，100 条约 9.3k，1000 条约 97k——token 成本和注意力都会先于性能出问题。
3. **图片数量是第二道硬闸。** 超过 20 张截图会被宿主拒绝；插件已加前置拦截。
4. **多图绘制是线性成本。** 20 张图约 488ms，仍然可接受；主要成本在每张图的解码 + 重绘 + 编码。

## 建议的产品边界

- 单张截图：**≤ 30 条标注**（超过时状态栏已有黄色提醒）。
- 单次插入：**≤ 5 张截图 / ≤ 150 条标注**；再多建议分批发送。
- 20 张截图为硬上限，由 DSH 附件策略决定；插件已拦截。
- 超过 100 条时，优先考虑把评论合并成段落（例如“这 12 个表单项统一……”），而不是每条一个编号。
